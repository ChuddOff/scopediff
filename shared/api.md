# ScopeDiff API v1 — единый контракт

Версия 1.0, 27.11.2026. Согласованные продуктовые решения плюс окончательные технические решения для MVP. Frontend: LeCodes TypeScript. Backend: FastAPI + PostgreSQL + DeepSeek. Все ключи JSON — camelCase; Python может использовать snake_case внутри с Pydantic aliases. Типы: `types.ts`.

## 1. Общие правила

- API base: `https://<backend>/api/v1`. HTML заказчика: `https://<backend>/share/<token>`. Адрес подставляется после деплоя.
- JSON UTF-8 по умолчанию. Импорты, создание предложения и revise используют `multipart/form-data` (`fetch` и `FormData` LeCodes). Не задавать multipart Content-Type вручную. Диктовка поля использует JSON. PDF отдаётся как `application/pdf`.
- Все private endpoints требуют `Authorization: Bearer <token>`, кроме `/session` и `/health`. Public endpoints авторизуются токеном в URL; не требуют пользовательского Bearer.
- ID генерирует сервер, UUID. Timestamp UTC ISO 8601; deadline — календарная дата YYYY-MM-DD. Неизвестный срок — null. Пустое текстовое поле — ''. Цена в целых рублях, null = не определена, 0 = явно бесплатно. Не показывать окончательный итог, если хотя бы одна цена не определена; можно показать известную сумму отдельно.
- Успех GET/PATCH/action — 200; создание ресурса — 201; удаление — 204 без тела. Массивы возвращаются напрямую, без pagination в MVP. Сортировка заказов/предложений — updatedAt DESC; услуг — name ASC; версий — version ASC.
- Ошибка: `{ "error": { "code": "AI_FAILED", "message": "Не удалось обработать запрос" } }`. Общий обработчик FastAPI приводит к этому формату и ошибки валидации. Не отдавать stack traces, SQL, ключи или ответ провайдера.
- HTTP 400 BAD_INPUT; 401 UNAUTHORIZED; 404 NOT_FOUND (включая чужие ресурсы); 409 VERSION_CONFLICT / OPEN_PROPOSAL_EXISTS / ORDER_CHANGED / INVALID_STATE; 413 FILE_TOO_LARGE; 422 VALIDATION_ERROR; 429 RATE_LIMITED; 502 AI_FAILED; 503 SERVICE_UNAVAILABLE. Клиент проверяет статус, не только исключения fetch. При 409 обновить данные и показать причину.
- Не повторять мутации автоматически после таймаута; при неопределённом исходе обновить список/карточку. Кнопки блокировать до ответа. Согласование идемпотентно на сервере.

## 2. Сессии и справочники

| Метод | Путь | Вход | Выход |
|---|---|---|---|
| GET | /health | — | {status:"ok"} либо 503 |
| POST | /session | {} | SessionResponse (201) |
| GET | /services | — | Service[] |
| POST | /services | ServiceInput | Service (201) |
| GET | /services/{id} | — | Service |
| PATCH | /services/{id} | Partial<ServiceInput> | Service |
| DELETE | /services/{id} | — | 204 |
| POST | /services/import | multipart | Service[] (201) |
| GET | /orders | — | OrderSummary[] |
| POST | /orders | OrderInput | Order (201) |
| GET | /orders/{id} | — | OrderDetail |
| PATCH | /orders/{id} | Partial<Pick<Order,"title"\|"serviceId"\|"agreements"\|"completedWork"\|"deadline"\|"status">> | Order |
| DELETE | /orders/{id} | — | 204 |
| POST | /orders/import | multipart | OrderImportResult (201) |

Сессия создаётся только при отсутствии токена на первом запуске. Случайный 256-битный токен, на сервере хранится SHA-256 хеш. Клиент сохраняет token в localStorage. При недоступности сервера не создавать новую сессию автоматически. После очистки локального хранилища доступ к старым данным без восстановления теряется: оговорка MVP.

ServiceInput требует только `name` (1–120 символов). `description` (до 12000) при пропуске получает значение `""`. Ответ содержит все поля Service. Импорт извлекает одну или несколько услуг и сохраняет их одной транзакцией; максимум 15 за импорт. Не добавлять придуманные цены/условия. Пользователь сразу видит каталог и может редактировать карточки.

OrderInput требует только `title` (1–160). Пропущенные `agreements` и `completedWork` (до 12000 каждый) получают значение `""`, `serviceId` и `deadline` получают `null`. Ответ содержит все поля Order. PATCH сохраняет пропущенные поля, а явный `deadline: null` очищает дату. При создании сервер проверяет serviceId и копирует снимок услуги. Снимок неизменяем; удаление услуги выставляет serviceId=null, но снимок остаётся. Изменение услуги не меняет заказы. При явной смене serviceId через PATCH сервер проверяет новую услугу, заменяет snapshot и увеличивает revision; при явном отвязывании serviceId=null очищает snapshot. Это позволяет исправить AI-выбор. Обычное редактирование/удаление самой услуги не переписывает снимок. Стандартные условия не означают автоматически согласованные индивидуальные условия: явно заданные договорённости заказа имеют приоритет.

Order.revision начинается с 1. Увеличивается при изменении контекста заказа (serviceId, agreements, completedWork, deadline) и успешном принятии предложения. Смена title сама по себе не меняет контекст. `openProposalStatus` вычисляется из единственного открытого предложения; null, если его нет. Список активных/завершённых фильтруется по status. Завершение требует отсутствия открытого предложения; повторное открытие через PATCH status=active.

Удаление заказа каскадно удаляет его предложения, версии и ссылки, с подтверждением в UI. Удаление услуги не удаляет заказы.

## 3. AI-операции

Четыре multipart-операции принимают `text` (необязательно, до 12000 символов), повторяющееся поле `files` (0–3 PNG/JPEG/WebP, до 5 MiB каждый и до 15 MiB суммарно), `serviceId` (только для /orders/import, необязательно), `expectedVersionId` (только для revise, обязательно). Нужен непустой текст или файл. Сервер определяет формат файла по содержимому, поэтому допустим `application/octet-stream`. Повреждённый файл возвращает `400 BAD_INPUT`, превышение числа или размера файлов — `413 FILE_TOO_LARGE`. Голос → SpeechRecognizer ru-RU → редактируемый текст → тот же API. Если устройство не поддерживает речь, показать ввод текста. Файлы не хранятся постоянно и не попадают в публичный документ.

| Метод | Путь | Ответ |
|---|---|---|
| POST | /services/import | Service[] (201) |
| POST | /orders/import | OrderImportResult (201) |
| POST | /orders/{id}/proposals | ProposalResult (201) |
| POST | /proposals/{id}/revise | ProposalResult (200) |
| POST | /ai/enhance-description | EnhanceDescriptionResult (200) |

### import_services
LLM получает текст и картинки; возвращает `{services:[{name,description}]}`. Сервер валидирует и сохраняет результат. При отсутствии услуг — 422, не создавать пустые карточки.

### import_order
LLM получает вход и выбранную услугу (если есть; иначе краткий список доступных услуг с ID для подсказки). Ответ:
```json
{
  "title":"Реклама кофейни",
  "suggestedServiceId":null,
  "agreements":"Вертикальный ролик до 60 секунд",
  "completedWork":"Первый вариант отправлен",
  "deadline":null,
  "detectedStage":"changes_requested",
  "proposal":{
    "title":"Дополнительная версия",
    "items":[{"title":"Горизонтальный ролик","description":"Версия 16:9","category":"extra","reason":"В договорённостях только 9:16","price":null}],
    "deadline":null,"conditions":"","comment":null
  }
}
```
`detectedStage`: new / in_progress / changes_requested / unknown (только результат AI). Если нет явно новых пожеланий — proposal=null. Если исходного ТЗ нет, категории не придумывать: unclear, если данных недостаточно. Не выдавать выполненную работу за согласованное требование. Валидировать suggestedServiceId; явно выбранная услуга всегда важнее рекомендации. Сохранить заказ и, если есть предложение, черновик версии 1 в одной транзакции. Возвращать сохранённые ID. UI сразу открывает заказ, без обязательной формы подтверждения.

### analyze_changes
LLM получает снимок услуги, исходные и индивидуальные договорённости, выполненные работы, текущий deadline, согласованные версии в хронологическом порядке и новый ввод. Согласованные последующие условия имеют приоритет над исходными; конфликтующие или отсутствующие сведения обозначаются как unclear. Ответ: ProposalContent без серверных ID пунктов. Сервер присваивает ID, создаёт предложение draft и версию 1. Не создавать пустой документ при отсутствии конкретных пожеланий.

### revise_proposal
LLM получает тот же контекст, текущую версию, новые замечания или команды исполнителя. Команда может указать порядковый номер исходного пункта, изменить его доплату, удалить его или добавить работу. Сервер проверяет ID и точные цитаты для изменений пунктов, цен, срока, названия, условий и комментария. Для скриншотов сначала извлекается текст. Неизменённые и отредактированные пункты сохраняют item.id, новые ID генерирует сервер. Сервер создаёт следующую версию со статусом предложения draft. Все предыдущие версии сохраняются, включая бывший черновик. expectedVersionId обязателен.

### enhance_description

Авторизованный JSON `EnhanceDescriptionInput`: `kind` (`service`, `order`, `change_item`, `conditions`), `title` (до 160 символов), `currentText` (до 12000), `dictation` (от 1 до 12000 после удаления крайних пробелов), `context` (до 48000). Все пять полей обязательны. `title`, `currentText` и `context` могут быть пустыми. AI применяет распознанную диктовку к одному полю и сохраняет прежние условия, которых команда не касается. Ответ `{"text":"…"}` содержит непустой текст до 12000 символов. Запись происходит только при сохранении формы штатным API. Действуют общие лимиты AI.

### Общие требования к AI
DeepSeek `deepseek-flash`, OpenAI-compatible Chat Completions, `response_format={"type":"json_object"}`, системный промпт явно требует JSON и нужную схему. Для скорости — non-thinking, если поддерживается (см. docs Thinking Mode); ограничить output до 4096 токенов. Изображения отправлять как base64 data URLs; проверять реальный формат/размер. Скриншоты и текст — недоверенные данные, не инструкции для модели. Не передавать API-ключ в модель. Валидация Pydantic обязательна: запрещать неверные enum, отрицательные/нецелые цены, выдуманные ID и даты. Одна повторная попытка при некорректном JSON (в рамках общего timeout); иначе 502. Без фиктивного успешного результата. AI никогда не утверждает согласование автоматически; цена только если явно задана, иначе null. Не использовать утверждение об оплате/юридическом обязательстве. `reason` — внутреннее обоснование классификации, не публикуется. Исходные изображения/тексты могут содержать персональные данные; перед отправкой показать краткое предупреждение, в логи не писать содержимое.

## 4. Предложения, версии и согласование

Для MVP **одно открытое предложение на заказ** (draft/pending/countered), любое число завершённых. Это исключает конкурирующие переговоры и уменьшает сложность. При наличии открытого предложения новое пожелание добавляется через revise к нему; UI предлагает открыть его. После approved/rejected можно создавать новое. Обеспечить ограничение в БД частичным unique index.

| Метод | Путь | Вход | Выход |
|---|---|---|---|
| GET | /orders/{id}/proposals | — | Proposal[] |
| GET | /proposals/{id} | — | ProposalDetail |
| PATCH | /proposals/{id} | UpdateProposal | ProposalResult |
| POST | /proposals/{id}/publish | PublishProposal | ProposalResult |
| POST | /proposals/{id}/approve | VersionAction | ProposalResult |
| POST | /proposals/{id}/reject | VersionAction | ProposalResult |
| POST | /proposals/{id}/revoke-link | VersionAction | ProposalResult |
| DELETE | /proposals/{id} | — | 204 (только ни разу не опубликованный draft) |
| GET | /versions/{id}/pdf | — | PDF file |
| POST | /versions/{id}/pdf-link | — | PdfLink |

Оба маршрута проверяют Bearer и владельца версии. `POST /versions/{id}/pdf-link` возвращает `200 {"url":"https://…","expiresAt":"…Z"}`. Открывайте `url` как есть во внешнем браузере без Bearer. Подписанный URL действует 10 минут и даёт доступ к PDF одной версии с зафиксированным при выдаче содержимым. Если это содержимое изменилось после выдачи, запросите новую ссылку. Просроченная или изменённая подпись возвращает `404`. Файл открывается с `Content-Disposition: inline`. Для экспорта черновика сначала запросите ссылку, затем вызовите `publish` с `format: "pdf"` и откройте URL после успешной публикации.

ProposalResult = {proposal, version}; ProposalDetail = {proposal, versions}. expectedVersionId — текущий ID версии, не её номер. Сервер проверяет принадлежность заказа/предложения/версии сессии, текущий статус и версию. При конфликте 409.

- draft: редактируется через PATCH (передаётся полное content; у новых пунктов id=null, существующие ID должны принадлежать предыдущей версии). Если текущая версия уже заморожена (pending/countered), PATCH создаёт новую версию freelancer draft, не перезаписывает предыдущую. Терминальные статусы не редактируются. Исторические версии неизменяемы.
- publish: формат pdf/markdown/text/link. Замораживает текущую версию, ставит pending, сохраняет publishedVersionId. Повторный publish той же pending версии допустим, не создаёт дубликат; при format=link генерирует стабильную ссылку, если ещё нет. Это «подготовлено к согласованию», а не доказательство отправки. PDF GET не меняет статус, можно предпросмотреть; перед передачей пользователю выполнить publish. При повторном экспорте используется конкретный ID версии.
- countered: встречное предложение клиента — новая неизменяемая версия author=client. Оригинал сохраняется. Исполнитель может принять, отклонить или подготовить свою версию (PATCH/revise → draft → publish). Новые условия не применяются до согласования.
- approve: допустимо pending/countered. Владелец вручную фиксирует внешнее согласование либо принимает встречное предложение; клиент может принять pending по ссылке. В одной транзакции заблокировать заказ/предложение, проверить expectedVersionId и baseOrderRevision, выставить approved и approvedVersionId, обновить срок заказа, если указан, увеличить order.revision. Повтор того же approve возвращает ранее согласованный результат без повторного применения; иной versionId → 409. Если контекст заказа изменился, 409 ORDER_CHANGED; revise или PATCH с проверкой контекста создаёт актуальный черновик. Согласованные предложения хранятся как отдельный журнал договорённостей (не перезаписывать исходный текст, не прибавлять цены в скрытую стоимость заказа). UI показывает исходный текст + согласованные изменения; AI учитывает последние согласованные условия. Неизвестные цены остаются неизвестными.
- reject: закрывает предложение без изменения заказа; ранее согласованные договорённости не затрагиваются. Не представлять статус как подтверждение личности заказчика.
- revoke-link: удаляет токен; ранее сохранённая ссылка перестаёт открываться, при новом publish link создаётся новый токен. Для терминального предложения разрешено отозвать ссылку, не меняя статус.
- При draft после публикации публичный URL остаётся прежним, показывает последнюю опубликованную версию read-only (`status:editing`), пока исполнитель не опубликует новую. В countered публичная страница показывает встречную версию read-only. В approved/rejected показывает окончательный статус. Не раскрывать новый неопубликованный черновик.

## 5. Публичная страница

HTML `GET /share/{token}` (без отдельного SPA, Jinja2 + CSS + JS). API:

| Метод | Путь | Вход | Выход |
|---|---|---|---|
| GET | /public/{token} | — | PublicProposal |
| POST | /public/{token}/respond | PublicResponse | PublicProposal |

Токен — случайный 256-битный, хранится в закрытой БД, уникален, не логируется. URL передаётся только владельцу и тем, кому он его отправил. Любой обладатель ссылки может отвечать, поэтому это не проверенная личность и не электронная подпись. В ответе только title, orderTitle, versionId, version, status, items (id/title/description/price), deadline, conditions, comment, canRespond. Не раскрывать serviceSnapshot, agreements, completedWork, внутренние reason/category, исходные изображения, session token, другие заказы. Без внешних скриптов/аналитики; no-store, no-referrer, noindex; экранирование HTML и безопасная вставка текста. Ограничить запросы, принимать JSON, проверять Origin на публичной странице.

`respond`: только pending и актуальный publishedVersionId. approve — атомарное согласование; counter — полный новый публичный документ со списком items, сроком, условиями, комментарием. Существующие ID должны принадлежать версии, новые id=null, отсутствующие — удалённые из предложения. При изменении содержания существующего пункта сбросить category в unclear и внутренний reason; при изменении только цены сохранить классификацию. Новым пунктам присвоить unclear. Сервер создаёт countered, новая версия client; заказчик не может изменить исходный документ. Старая версия, повторный ответ на уже обработанную версию или отозванный токен → 409/404. Суммы рассчитывает код. Мобильное приложение обновляет данные при возврате на экран и по кнопке обновления; push/WebSocket не нужны.

## 6. PDF и экспорт

ReportLab, один шаблон A4 с кириллическим TTF-шрифтом (например, DejaVu Sans, установить/включить с лицензией в серверный образ). Версия, дата, название заказа, перечень работ, описания, доплаты, срок, условия. Нейтральный заголовок «Предложение по изменениям», не юридический договор. Не показывать приватные причины AI и внутренние заметки; отображать категории нейтрально при необходимости, цены null — «Не определена». Длинный текст переносится, таблица и страницы не обрезаются. MIME application/pdf, Content-Disposition attachment с именем scopediff-<id>-v<N>.pdf. Markdown/plain text генерирует клиент из тех же данных, без повторного AI. Проверить `share()` файла из fetch на реальном телефоне; если PDF недоступен, текст — обязательный запасной путь. Интерактивная ссылка дополнительна, не требуется для основного сценария.

## 7. База, безопасность и запуск

FastAPI, SQLAlchemy 2.0 sync + psycopg, Alembic, PostgreSQL, Pydantic 2, OpenAI Python SDK, ReportLab, Jinja2, python-multipart, Pillow. Синхронные DB операции не держать в транзакции во время AI-вызова; AI можно вызвать async с короткими DB этапами через threadpool или реализовать sync route с обычным OpenAI client. Не блокировать event loop. Docker Compose: api + db (persistent volume); внешний HTTPS через выбранный хостинг. Миграции при деплое. `sessions`, `services`, `orders`, `proposals`, `proposal_versions`; JSONB для serviceSnapshot и items; внешний ключ с проверкой владельца, unique(proposal_id,version), частичный unique открытого предложения. Транзакции/row locks для approve/respond/publish/revise, повторно проверить версию и ревизию после AI вызова. Не держать блокировку на время AI. Хранить токены/ключи отдельно от исходного кода; .env в .gitignore, .env.example без секретов.

## 8. Приёмка

1. Новый пользователь без регистрации получает сессию и пустой список; повторный запуск сохраняет данные.
2. Создать услугу вручную и импортировать две из текста/изображения; карточки редактируются, описание хранится.
3. Создать заказ с/без услуги, изменение/удаление услуги не меняет snapshot.
4. Импорт заказа без правок создаёт только заказ; с правками — заказ и готовый черновик. Неизвестная цена null, а не 0.
5. Анализ новых правок учитывает реальные условия и выполненную работу; документ редактируется, экспортируется и открывается на телефоне.
6. Замечания создают новую версию; предыдущая доступна. Согласование обновляет срок и журнал один раз, последующий AI учитывает его.
7. Публичная ссылка (если реализована) открывается без регистрации, ответ клиента виден в приложении, предыдущая версия неизменна. Старые/отозванные ссылки и доступ к чужим ресурсам проверяются.
8. Отключение сети, отказ микрофона, ошибка AI, неизвестная стоимость, длинный текст и пустые состояния обрабатываются без краша. Не показывать неработающие кнопки.
9. Публикация в LeStore, реальный телефон, запись сценария, доступный внешний backend и AI на период оценки; опубликованная версия остаётся в LeStore без ограничения срока.
